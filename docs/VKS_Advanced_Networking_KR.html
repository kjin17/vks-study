멀티 NIC은 「두 개의 층」이다

이걸 안 가르면 설계도 트러블슈팅도 어긋납니다
Layer 2 · 인프라

노드 보조 NIC (eth1~eth9)

  • 단위 = 노드 VM. 그 노드의 모든 파드가 공유
  • CAPV / vm-operator 가 담당 — CNI 와 무관
  • networks 변수로 선언 · VKS 3.6
  • 쓰는 곳 : NFS 스토리지·DB 복제 등 노드 전체 트래픽 분리
Layer 3 · 파드

파드 멀티 NIC (net1, net2 …)

  • 단위 = 개별 파드. 파드마다 전용 인터페이스·전용 IP
  • Multus(VKS 3.7) 또는 Antrea SecondaryNetwork(3.6)
  • NetworkAttachmentDefinition + 파드 어노테이션
  • 쓰는 곳 : CNF·멀티캐스트 등 특정 워크로드 전용 경로
!
eth1 을 붙여도 트래픽은 안 나뉩니다. 파드는 계속 eth0 을 쓰고, eth1 에는 기본 경로가 없습니다. 보안 가치는 위상에 있습니다 — API 서버는 eth0 서브넷에서만 듣기 때문에, eth1 에만 연결된 것은 컨트롤 플레인에 물리적으로 닿지 못합니다.

Step 1 · AddonInstall

Supervisor 의 클러스터 네임스페이스에 생성
  • CEL 제약으로 「CNI 참조가 cilium 이고 K8s 1.35 이상」일 때만 매칭
  • 조건을 벗어난 클러스터에 실수로 붙는 것을 막아 줍니다
  • ownerReference 를 걸어 클러스터와 함께 지워지게 하세요
addoninstall-cilium.yaml
apiVersion: addons.kubernetes.vmware.com/v1alpha1 kind: AddonInstall metadata: name: <cluster-name>-cilium namespace: <cluster-namespace> spec: addonRef: name: cilium clusters: - constraints: expression: "cluster.cniRefName() == 'cilium' && version_in_range(cluster.spec.topology.version, '>=1.35.0')" selector: matchLabels: cluster.x-k8s.io/cluster-name: <cluster-name> stopMatchingBehavior: Retain
$ kubectl apply -f addoninstall-cilium.yaml $ kubectl get addoninstall <cluster-name>-cilium -n <ns>

kube-proxy 비활성화 API

VKS 3.7 · Cilium 의 eBPF 서비스 구현으로 kube-proxy 를 대체
spec.topology.variables
- name: kubernetes value: kubeProxyConfiguration: enabled: false
스펙과 제약
# 적용 범위 cluster 스코프만 # 변경 가능성 immutable # 변경 영향 머신 롤아웃 # CNI 제약 Antrea · KR 내장 Calico 미지원 # 커스텀 CNI 는 KR 1.35 이상
  • 이 기능들은 kube-proxy 가 켜져 있으면 검증 오류가 납니다 (Cilium 1.19.4)
    • L7 프록시 (Envoy 기반 L7 정책)
    • Ingress 컨트롤러 · Gateway API 컨트롤러
    • Egress Gateway (SNAT)
    • eBPF 마스커레이딩
  • 즉 「Cilium 의 좋은 기능을 쓰고 싶다」는 요구는 곧 「클러스터를 만들 때 kube-proxy 를 끄고 시작해야 한다」는 설계 결정입니다

Hubble 3층 구조

hubble.enabled 가 기본 true 라 켜져 있다고 읽기 쉽지만, 그건 노드 단위 서버만 돌고 있다는 뜻입니다. 클러스터 전체를 한눈에 보는 경험(Relay · UI)은 명시적으로 켜야 생깁니다. 그리고 Relay 는 각 노드의 TCP 4244 로 붙습니다 — 워커에 이 포트가 안 열려 있으면 Relay 는 Running 인데 그 노드 플로우만 조용히 빠집니다.

접근 · 검증

Hubble 의 실전 가치는 대시보드 구경이 아니라 「왜 막혔는가」를 즉시 답하는 것
UI · CLI 접근
# UI (ClusterIP 기본) $ kubectl port-forward -n kube-system svc/hubble-ui 12000:80 # Relay 에 붙어 플로우 보기 $ kubectl port-forward -n kube-system svc/hubble-relay 4245:80 $ hubble observe --server localhost:4245 -f # 정책 때문에 막힌 트래픽만 $ hubble observe --verdict DROPPED --type policy-verdict
검증 — 노드 수를 대조
$ hubble status --server localhost:4245 # 연결된 노드 수 == 실제 노드 수 인가?
  • 파드가 Running 인 것은 「떴다」이지 「보고 있다」가 아닙니다. 4244 가 일부 노드풀에만 열려 있으면 Relay 는 정상 기동한 채로 그 노드들의 플로우를 빠뜨립니다 — 에러로 안 나타납니다
  • Hubble UI 에는 인증이 없습니다. LoadBalancer 로 열면 네트워크에 닿는 누구나 클러스터 전체 통신 그래프를 봅니다
  • 보조 NIC 에는 LoadBalancer 를 못 붙입니다 — Service type LoadBalancer 는 항상 primary 에 생깁니다
  • Hubble 은 기본적으로 링 버퍼 — 장기 보관 도구가 아닙니다. 과거 사건 조사는 메트릭·로그로 따로 내보내세요

networks 변수 · 인프라 준비

NSX VPC 는 Subnet/SubnetSet, VDS 는 Network — API 그룹만 다르고 패턴은 같습니다
① NSX VPC · Subnet (클러스터 생성 전)
kind: Subnet # crd.nsx.vmware.com/v1alpha1 spec: accessMode: Private subnetDHCPConfig: mode: DHCPDeactivated # 필수 advancedConfig: staticIPAllocation: enabled: false # 필수 · IP 고갈 방지
② Cluster · spec.topology.variables
- name: networks value: interfaces: secondary: # primary 생략이 기본 - name: eth1 # eth0 불가 · mtu 9000 = 점보 network: apiVersion: crd.nsx.vmware.com/v1alpha1 kind: Subnet name: secondary-node-net
  • staticIPAllocation: false 는 권고가 아니라 필수입니다. 켜져 있으면 노드가 프로비저닝될 때마다 정적 IP 를 소비하는데 롤링 업데이트에서 반환되지 않아 서브넷이 고갈됩니다
  • VDS 는 포트그룹 3종을 모두 — trunk 모드 · Forged Transmits · MAC Learning. 둘만 맞춰도 노드는 정상으로 뜨고, 고장은 나중에 파드 보조 NIC 통신 불가로 나타납니다. 이걸 가리키는 이벤트나 에러가 없어 디버깅이 가장 긴 지점입니다
  • primary 는 영구입니다 — 생성 후 변경 불가. SubnetSet 만 참조 가능하고, 대부분의 배포는 생략이 정답입니다
  • eth1 에 목적을 주려면 routes(to / via) 를 추가합니다 — CloudInit 부트스트랩 전용 · IPv4만
  • 기존 클러스터에 추가는 가능합니다 — 롤링 노드 업데이트로 적용
